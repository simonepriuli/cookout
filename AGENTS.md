# AGENTS.md

The cookout: a self-hosted, Slack-style board for people and agents. Spec: mattpocock/cookout#1.

- [GLOSSARY.md](GLOSSARY.md): the domain language. Names in code use its terms.
- `pnpm check` runs the checks CI runs through `scripts/check.ts`, browser tests included. The e2e suite (`packages/e2e` on the Docker image) runs only on CI, as its `e2e-docker` job ([ADR](docs/adr/0088-the-e2e-suite-runs-only-on-ci.md)); run it on purpose with `pnpm e2e:docker`. Pack smoke and the published client are CI-only jobs too. Run `pnpm check` once before you finish; it must exit 0. Before its verdict it prints one `skipped:` line naming the e2e suite. Locally it runs only the browser tests the branch reaches, and runs them all when it can't tell ([ADR](docs/adr/0092-local-check-runs-only-the-browser-tests-a-branch-reaches.md)); CI runs them all. When it skips some, a second `skipped:` line names them; `pnpm browser` runs them all. Its last line is its verdict, after any time budget warnings: `RESULT: PASS` or `RESULT: FAIL (<failed checks>)`. It waits while another `pnpm check` or `pnpm coverage:changed` runs on the machine, printing one line on stderr that names the worktree it waits for (CI doesn't wait).
- `pnpm coverage:changed` runs the tests and lists, as `file:line`, every uncovered line or branch in files changed against v1. Run it before `pnpm check` to catch a coverage gap early. It waits for the same machine-wide lock as `pnpm check`.
- `pnpm merge-ticket <N>` merges ticket-N into v1. If it stops on a conflict, resolve it and commit on merge-ticket-N, then run `pnpm merge-ticket <N> --continue`: it checks and pushes. Its local check is only the fast ones (types, lint and hygiene, which holds the migration and ADR guards); CI is the merge's full check. It pushes the merge to merge-ticket-N (or, if origin already has merge-ticket-N at that commit, doesn't push it again), waits for that branch's Check run, and only when every job is green fast-forwards v1 to that exact commit (never forced), then deletes merge-ticket-N. If v1 moved, either run merges the new v1 into your merge, keeping your fixes, and stops only if that merge conflicts; if merge-ticket-N's run is red, it stops and prints the failed jobs, with nothing pushed to v1, and leaves merge-ticket-N on origin. A flaky job is retried once, the same way for both runs: a red ticket-N run on the commit merge-ticket judges (on a fresh run or `--continue` alike), and on `--continue` a red merge-ticket-N run on an unchanged commit, get their failed jobs rerun once (`gh run rerun <id> --failed`), and the rerun is judged, so a rerun never needs a new commit; a moved merge-ticket-N commit waits for its own run instead. A job skipped because a job it needs failed isn't named as failed; a skipped job blocks only when every other job passed. Never rerun a job by hand. Before its check, it runs `pnpm install --frozen-lockfile` if the merged `pnpm-lock.yaml` differs from ticket-N's. It refuses to merge while v1's latest Check run or ticket-N's has a job that is not green, waiting for a run still in progress, except that a v1 run in progress or cancelled on a commit already green on a `merge-ticket-*` branch counts as green, and a run cancelled by a newer push is judged by that newer run; only the ticket that fixes a red v1 passes `--fixes-red-v1`. It refuses a merge whose migrations list doesn't begin with origin/v1's, entry for entry; only a ticket that moves a migration production hasn't run passes `--reorders-undeployed-migrations`, which compares with the newest `deploy/*` tag instead. Its last line is its verdict: `RESULT: MERGED <sha>` after the fast-forward push, or `RESULT: FAIL (<failed step or jobs>)`. After the fast-forward push it prints the merge SHA and exits 0, without waiting for v1's own run of that already-green commit.
- `pnpm ci:wait` waits for the Check push run of HEAD, polling every 30 s, prints each job's conclusion and each failed job's failed steps and last 20 log lines, and exits 0 only if every job passed (a job that failed only on a time budget warns). Its last line is its verdict: `RESULT: PASS` or `RESULT: FAIL (<failed jobs>)`. It judges the commit, not one run: the commit is green if any completed run on it succeeded, a cancelled run never counts as red, and if every run on it was cancelled it reruns the newest once; merge-ticket's waits do the same. `pnpm ci:wait --sha <sha> --branch v1` watches a merge on v1. Use it to wait for CI; never hand-write `gh run watch`, and never pipe a watch, since a pipe hides its exit code.
- `pnpm lint:changed` runs the hook's lint (same rules and baseline ratchet) and type check on files changed against origin/v1, staged, unstaged or untracked, without committing or fixing. It prints each new violation once, in the hook's format (including ones the hook would fix for you), and exits non-zero if there are any. Run it while you work to see lint early.
- Don't run fix, format or other lint commands yourself. Commit, and the pre-commit hook fixes and formats what you staged; then fix by hand only what it prints as left over: each new violation once, as `file:line rule message`, then "N new violations in M files". Commit with `scripts/commit.sh`, which takes `git commit`'s arguments: lefthook skips the whole hook when nothing is staged, so it fails then with "nothing staged: run git add first".

- Only Matt approves a domain term. A term counts as approved only with a dated decision of Matt's cited next to it, in an ADR under `docs/adr/` or a comment on a mattpocock/cookout issue; without one it stays proposed.
- In a git worktree, create files with the Write tool (not `cat > … <<EOF`), run every command from the worktree root, and add root dependencies with `pnpm add -w`.
